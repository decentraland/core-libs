Bound the entity file with a per-entity-type allowance. `createSizeValidateFn` now rejects a deployment whose entity file exceeds `maxEntityFileSizeInKB` for its type, reporting the limit and the size that was uploaded.

Previously nothing bounded the entity file at all. `calculateDeploymentSize` sums the hashes listed in `entity.content`, and the entity file is excluded from content accounting by design — it is keyed by `entity.id`, and `allHashesInUploadedFilesAreReportedInTheEntityValidateFn` allows it precisely because it is not a content mapping. So the ADR-51 cap only ever measured a deployment's assets. The effect was largest for profiles, which since ADR-290 carry no content files at all: their measured size is always `0` regardless of metadata, so a 20 MB profile validated against a 2 MB cap, and the only authorization for deploying one is pointer == signer. The entity file is stored and persisted like any other, so the unbounded value reached content storage, `entity_metadata`, and the active-entity cache.

A `maxLength` in `@dcl/schemas` would not have closed this: `additionalProperties: true` on Scene, Profile and Avatar lets arbitrary extra keys carry the same payload, and `content[].file` has no `maxLength` either, so a long content mapping inflates the entity just as well. The limit is therefore applied to the entity file as a whole rather than to metadata or to any individual field.

The allowance is separate from `maxSizeInMB` rather than folded into it, so metadata never competes with a deployment's assets: a scene may still use its full 15 MB content budget alongside its entity file, which would not have been true had the entity bytes simply been added to the existing total. The limits are per type because the entity file means something different in each: `scene` 2048 KB, sized for the content mapping rather than the metadata, since an estate spanning 10k parcels at the 3000-file upload limit serialises to about 512 KB of which only ~3 KB is metadata; `wearable` and `emote` 512 KB, leaving headroom for the legitimately large `mappings` of linked wearables, where 5000 ranges is about 218 KB; `profile` 256 KB against roughly 7 KB for a profile with 40 wearables and 10 emotes; `outfits` 256 KB against about 28 KB for all ten slots filled; `store` 128 KB.

The rule is gated on the new `ENTITY_FILE_SIZE_TIMESTAMP` constant, a fixed `2026-09-01T00:00:00Z` overridable through the `ENTITY_FILE_SIZE_TIMESTAMP` environment variable like the existing ADR timestamps. Entities older than the cutoff keep validating, so a node re-validating historical content while bootstrapping does not reject deployments that were accepted under the previous accounting. A new deployment cannot be dated before the cutoff to evade the rule: the catalyst bounds a submitted `entity.timestamp` to `REQUEST_TTL_BACKWARDS`, 20 minutes by default, behind wall-clock.
